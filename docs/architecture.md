# 1. معرفی محصول (Product Overview)

پایدارپرس یک افزونه مستقل وردپرس برای شناسایی، تحلیل، برنامه‌ریزی، تولید، بهینه‌سازی و مدیریت هوشمند محتوای وب‌سایت‌ها با استفاده از مدل‌های مختلف هوش مصنوعی است.

این افزونه با هدف ارائه یک ابزار جامع برای مدیریت محتوای وب‌سایت‌های وردپرسی طراحی می‌شود و قابلیت استفاده در انواع وب‌سایت‌ها را دارد.

پایدارپرس به هیچ سیستم مدیریت محتوای مرکزی وابسته نیست و هر نسخه آن به‌صورت مستقل روی وب‌سایت مشتری نصب و اجرا می‌شود.

ارتباط با PaydarWP صرفاً برای مواردی مانند مدیریت لایسنس، دریافت بروزرسانی و خدمات تجاری محصول خواهد بود.

## 1.1 اهداف اصلی

1. شناسایی خودکار ساختار و محتوای وب‌سایت.
2. استخراج و نگهداری موجودی مقالات، محصولات، دسته‌بندی‌ها و برچسب‌ها.
3. ایجاد پروفایل هوشمند از کسب‌وکار و محتوای وب‌سایت.
4. تحقیق وب و پیشنهاد موضوعات جدید برای تولید محتوا.
5. دریافت تأیید مدیر برای موضوعات پیشنهادی.
6. تولید خودکار مقالات بر اساس برنامه زمانی.
7. انتشار خودکار مقالات پس از اعتبارسنجی.
8. تولید محتوای محصولات ووکامرس.
9. تولید و بهینه‌سازی توضیحات دسته‌بندی‌ها.
10. تحلیل وضعیت سئو و بروزرسانی محتوا.
11. تولید گزارش‌های ساختاریافته JSON.
12. پشتیبانی از ارائه‌دهندگان مختلف هوش مصنوعی.
13. ساخت خودکار پروفایل سایت، به‌طوری‌که مدیر فقط اطلاعاتی را وارد کند که از سایت قابل استخراج نیست.
14. ممیزی سلامت محتوا بدون نیاز به هوش مصنوعی و هزینه API.
15. تبادل دوطرفه داده با ContentMaster: خروجی برای پرامپت و ورود نتایج آن به‌صورت پیش‌نویس.

## 1.2 انواع وب‌سایت‌های هدف

- وب‌سایت‌های معمولی WordPress
- وب‌سایت‌های محتوایی و مجلات
- فروشگاه‌های WooCommerce
- وب‌سایت‌های خدماتی
- وب‌سایت‌های چندزبانه

قابلیت‌های اختصاصی هر پلتفرم باید از طریق ماژول‌های مستقل فعال شوند.

# 2. اصول معماری (Architecture Principles)

معماری پایدارپرس باید بر اساس اصول زیر طراحی شود:

### 2.1 Modular Architecture

هر قابلیت باید در یک ماژول مستقل پیاده‌سازی شود.

اضافه کردن قابلیت جدید نباید نیازمند تغییر گسترده در هسته افزونه باشد.

### 2.2 Provider Independence

هسته افزونه نباید به یک مدل یا شرکت هوش مصنوعی وابسته باشد.

ارتباط با OpenAI، Anthropic، xAI، Google و ارائه‌دهندگان آینده از طریق لایه مستقل Provider انجام می‌شود.

### 2.3 WordPress Native Compatibility

برای عملیات مربوط به مقالات، صفحات، دسته‌بندی‌ها، برچسب‌ها و محصولات باید تا حد امکان از APIهای استاندارد WordPress و WooCommerce استفاده شود.

### 2.4 Human Approval

موضوعات پیشنهادی قبل از ورود به چرخه تولید باید به تأیید مدیر برسند.

انتشار خودکار محتوا فقط پس از تأیید موضوع و عبور محتوا از مراحل اعتبارسنجی مجاز است.

### 2.5 Asynchronous Processing

عملیات زمان‌بر مانند تحقیق موضوع، تولید مقاله، تحلیل محصولات و تولید گزارش نباید به یک درخواست PHP وابسته باشند.

تمام این عملیات باید از طریق سیستم صف پردازش اجرا شوند.

### 2.6 Data Ownership

اطلاعات سایت متعلق به مشتری است.

اطلاعات محتوایی فقط برای اجرای درخواست‌های مشخص‌شده به سرویس هوش مصنوعی ارسال می‌شوند.

### 2.7 Extensibility

معماری باید امکان افزودن قابلیت‌های آینده مانند تحلیل تصاویر، لینک‌سازی داخلی هوشمند، تولید FAQ و تحلیل رقبا را فراهم کند.

### 2.8 Single Source of Prompt Truth

منطق تولید محتوا در یک پرامپت مرجع به نام **ContentMaster** نگهداری می‌شود.

مسترپرامپت‌های وظیفه‌محور افزونه (PM-001 تا PM-006) از هسته مشترک ContentMaster و پروفایل سایت استفاده می‌کنند و فقط دستورالعمل اختصاصی وظیفه و قالب خروجی ساختاریافته را اضافه می‌کنند.

هر بهبود در ContentMaster باید هم در استفاده دستی (Claude و سایر چت‌ها) و هم در افزونه قابل اعمال باشد.

### 2.9 Persian & Iran Readiness

افزونه از ابتدا برای سایت‌های فارسی و شرایط میزبانی در ایران طراحی می‌شود:

- نرمال‌سازی متن فارسی در تمام مقایسه‌ها و تشخیص‌ها (بخش 4.7)
- پشتیبانی از تاریخ و سال شمسی در تشخیص محتوای قدیمی
- پشتیبانی از اسلاگ‌های فارسی (URL-encoded)
- امکان ارتباط با سرویس‌های خارجی از طریق Relay/Proxy (بخش 4.3)
- عملکرد کامل بخش‌های غیر هوش مصنوعی (اسکن، ممیزی، خروجی) بدون نیاز به اتصال خارجی

### 2.10 Safe Publishing

سطح خودکارسازی انتشار بر اساس حساسیت محتوای سایت تعیین می‌شود.

برای سایت‌های YMYL (حقوقی، پزشکی، مالی) پیش‌فرض، ایجاد پیش‌نویس و بازبینی انسانی است و انتشار خودکار فقط با تصمیم صریح مدیر فعال می‌شود.

هیچ محتوایی حاوی لینک به آدرس‌های ناموجود، موضوع تکراری یا موضوع ممنوع منتشر نمی‌شود.

### 2.11 Coexistence with PaydarWP Products

ممکن است چند محصول PaydarWP (مانند پایدار کارت یا هدر و فوتر) هم‌زمان روی یک سایت نصب شوند. هیچ شناسه‌ای نباید بین محصولات مشترک باشد، مگر شناسه‌های عمداً مشترک PaydarWP Hub.

| مورد | قاعده در پایدارپرس |
|---|---|
| جداول دیتابیس | `{$wpdb->prefix}paydarpress_*` |
| Optionها و Transientها | `paydarpress_*` |
| Post Meta و Term Meta | `_paydarpress_*` |
| Hookها (Action و Filter) | `paydarpress/*` |
| Capabilityها | `paydarpress_*` |
| REST API Namespace | `paydarpress/v1` |
| گروه Action Scheduler | `paydarpress` |
| PHP Namespace | `PaydarWP\PaydarPress` |
| Text Domain | `paydarpress` |
| کلاس‌های CSS و Handle اسکریپت‌ها | `paydarpress-*` |
| Cron Hookها | `paydarpress_*` |

**PaydarWP Hub (کتابخانه مشترک)**

بخش‌های مشترک بین محصولات در یک کتابخانه کوچک قرار می‌گیرند که درون هر محصول قرار دارد:

- ثبت منوی سطح اول «پایدار وردپرس» (`paydarwp`)
- صفحه لایسنس و بروزرسانی محصولات
- Design Tokenها و فایل‌های فونت وزیرمتن

اگر چند محصول نسخه‌های متفاوتی از Hub داشته باشند، فقط **جدیدترین نسخه** بارگذاری می‌شود (مانند روش Action Scheduler). منو فقط یک بار ثبت می‌شود و هر محصول فقط زیرمنوی خود را اضافه می‌کند.

حذف یک محصول نباید داده‌ها، جداول یا منوی مشترک سایر محصولات را حذف کند. منوی «پایدار وردپرس» با حذف آخرین محصول PaydarWP از بین می‌رود.

# 4. ساختار ماژول‌ها (Module Architecture)

## 4.1 Core Module

هسته اصلی پایدارپرس مسئول مدیریت چرخه عمر افزونه و ارتباط میان ماژول‌ها است.

وظایف:

- راه‌اندازی افزونه
- مدیریت تنظیمات عمومی
- ثبت و فعال‌سازی ماژول‌ها
- مدیریت دسترسی کاربران
- مدیریت رویدادهای داخلی
- مدیریت نسخه و بروزرسانی
- بررسی وابستگی‌ها

هسته نباید شامل منطق اختصاصی تولید مقاله یا ارتباط مستقیم با API یک ارائه‌دهنده هوش مصنوعی باشد.

## 4.2 Site Intelligence Module

این ماژول مسئول شناخت وب‌سایت است.

اطلاعات موردنیاز:

**Site Information**
- نام سایت
- دامنه
- زبان اصلی
- منطقه زمانی
- توضیحات سایت
- ساختار پیوندهای یکتا
- قالب فعال
- نسخه وردپرس
- افزونه‌های مرتبط

**Content Inventory**
- مقالات
- صفحات
- محصولات
- وضعیت انتشار
- تاریخ ایجاد و ویرایش
- عنوان و اسلاگ
- کلمات کلیدی
- توضیحات متا
- محتوای اصلی

**Taxonomy Inventory**
- دسته‌بندی مقالات
- دسته‌بندی محصولات
- برچسب‌ها
- ارتباط دسته‌بندی‌های والد و فرزند
- تعداد محتوای مرتبط

**Media Inventory**
- تصاویر
- آدرس تصاویر
- متن جایگزین
- کپشن
- ابعاد
- ارتباط تصویر با محتوا

**Internal Link Inventory**
- لینک‌های داخلی
- لینک‌های خارجی
- صفحات بدون لینک داخلی
- صفحات دریافت‌کننده لینک

**Site Structure (جدید)**
- منوهای سایت و آیتم‌های آن‌ها (برای تشخیص صفحات کلیدی و ساختار سایت)
- صفحه اصلی و صفحه نوشته‌ها
- نوع‌های نوشته سفارشی (Custom Post Types) و Taxonomyهای سفارشی، مانند آگهی‌ها یا خدمات
- ریدایرکت‌ها از Rank Math، Yoast Premium یا افزونه Redirection

**اطلاعات تکمیلی هر محتوا (جدید)**
- دسته‌بندی اصلی (Primary Category از Yoast یا Rank Math)
- کلمه کلیدی اصلی و کلمات کلیدی فرعی
- عنوان سئو، Meta Description، Canonical، وضعیت noindex و Cornerstone
- سرفصل‌های H2 و H3 (Outline)
- تعداد کلمات و خلاصه کوتاه
- سال‌ها و اعداد زمان‌دار ذکرشده در عنوان و متن (شمسی و میلادی)
- وجود تصویر شاخص و متن جایگزین آن

**گراف لینک داخلی (جدید)**

لینک‌ها به‌صورت گراف ذخیره می‌شوند (مبدأ، مقصد، انکرتکست).

از این گراف موارد زیر محاسبه می‌شود:

- تعداد لینک ورودی و خروجی هر محتوا
- محتوای یتیم (بدون لینک ورودی)
- لینک به آدرس‌های ریدایرکت‌شده یا ناموجود

### استخراج محتوا از صفحه‌سازها

محتوای ساخته‌شده با صفحه‌سازها همیشه به‌صورت کامل در `post_content` ذخیره نمی‌شود.

برای هر صفحه‌ساز یک Content Extractor اختصاصی در نظر گرفته می‌شود:

| صفحه‌ساز | منبع داده |
|---|---|
| Gutenberg / Classic | `post_content` |
| Elementor | `_elementor_data` (JSON) |
| WPBakery | Shortcodeهای `post_content` |
| سایر | خروجی رندرشده (Fallback) |

### اسکن و ذخیره‌سازی

این اطلاعات باید به‌صورت ساختاریافته ذخیره و در زمان نیاز بروزرسانی شوند.

اسکن اولیه باید کامل باشد و اسکن‌های بعدی ترجیحاً به‌صورت افزایشی انجام شوند. تغییرات از طریق Hookهای `save_post`، `deleted_post` و `edited_term` ثبت شده و فقط محتوای تغییرکرده دوباره اسکن می‌شود.

متن کامل محتوا در Inventory کپی نمی‌شود. متن اصلی همیشه از جداول وردپرس خوانده می‌شود و Inventory فقط داده‌های مشتق‌شده (آمار، Outline، لینک‌ها و پرچم‌ها) را نگهداری می‌کند.

## 4.3 AI Provider Manager

این ماژول مسئول مدیریت ارتباط با مدل‌های هوش مصنوعی است.

ارائه‌دهندگان اولیه:

| Provider | قابلیت |
|---|---|
| OpenAI | تولید و تحلیل |
| Anthropic | تولید و تحلیل |
| xAI | تولید و تحلیل |
| Google Gemini | تولید و تحلیل |
| سایر ارائه‌دهندگان | از طریق Adapter |

وظایف:

- ذخیره تنظیمات Provider
- مدیریت API Key
- انتخاب مدل
- ارسال درخواست
- دریافت پاسخ
- مدیریت Timeout
- مدیریت خطا
- Retry
- ثبت مصرف و هزینه تخمینی
- کنترل محدودیت درخواست‌ها
- پشتیبانی از Custom Base URL و Relay/Proxy برای هر Provider
- تست اتصال از داخل تنظیمات

تمام Providerها باید خروجی استاندارد داخلی پایدارپرس تولید کنند.

### Relay / Proxy

در بسیاری از هاست‌های داخل ایران، ارتباط مستقیم با APIهای خارجی برقرار نمی‌شود.

برای هر Provider، و همچنین Search Provider و سرور لایسنس، امکان تعیین یک آدرس واسط وجود دارد.

API Key از طریق Relay عبور می‌کند. بنابراین در رابط کاربری باید به مدیر هشدار داده شود که فقط از Relay مورد اعتماد استفاده کند.

### Search Provider

Search Provider به‌عنوان Adapter مستقل تعریف می‌شود.

اگر API یک ارائه‌دهنده هوش مصنوعی ابزار جستجوی وب داخلی داشته باشد، می‌توان آن را نیز به‌عنوان یک Search Provider ثبت کرد.

در هر حالت، منابع تحقیق باید همراه پیشنهادها ذخیره شوند.

### Task Routing – استفاده هم‌زمان از چند API (جدید)

پایدارپرس به یک Provider محدود نیست. هر وظیفه می‌تواند از Provider و مدل جداگانه استفاده کند تا کیفیت لازم با کمترین هزینه به دست آید.

**توانایی‌ها (Capabilities)**

هر Provider و مدل هنگام ثبت، توانایی‌های خود را اعلام می‌کند:

| توانایی | کاربرد |
|---|---|
| `text` | نگارش، تحلیل، طبقه‌بندی |
| `image_generation` | تولید تصویر |
| `vision` | خواندن تصویر (تولید Alt دقیق) |
| `embedding` | تشخیص تکرار و یافتن محتوای مرتبط |
| `web_search` | تحقیق وب داخلی مدل (در صورت پشتیبانی) |
| `batch` | ارسال گروهی با هزینه کمتر |
| `prompt_cache` | کش بخش ثابت پرامپت |

**OpenAI-Compatible Adapter**

بسیاری از سرویس‌های ارزان‌تر و واسط‌ها ساختار درخواست سازگار با OpenAI دارند. یک Adapter عمومی با Base URL، API Key و نام مدل قابل تنظیم، اتصال به این سرویس‌ها را بدون توسعه Adapter جدید ممکن می‌کند.

**جدول مسیریابی پیش‌فرض**

| وظیفه | سطح مدل | توضیح |
|---|---|---|
| تحقیق موضوع | قوی + `web_search` یا Search Provider | نیاز به استدلال و داده زنده |
| تشخیص تکرار | `embedding` + مدل ارزان | ابتدا شباهت برداری، سپس قضاوت مدل ارزان فقط برای موارد مشکوک |
| نگارش مقاله | قوی | کیفیت متن مهم‌ترین عامل است |
| **بریف تصویر** | **همان مدل نگارش مقاله، در همان درخواست** | بدون درخواست اضافه (توضیح پایین) |
| تطبیق پرامپت با مدل تصویر | ارزان (اختیاری) | تبدیل بریف به قالب پرامپت مناسب مدل تصویرساز انتخاب‌شده |
| تولید تصویر | `image_generation` | مدل تصویرساز |
| Alt تصاویر جدید | **همان مدل نگارش، همراه بریف تصویر** | بدون درخواست اضافه |
| Alt تصاویر موجود | ارزان (متنی) یا ارزان با `vision` | بر اساس روش انتخاب‌شده در بخش 4.8.4 |
| توضیحات دسته‌بندی | متوسط | |
| توضیحات محصول | متوسط یا قوی | بسته به اهمیت محصول |
| کپشن شبکه‌های اجتماعی | ارزان | متن کوتاه از خلاصه مقاله |
| طبقه‌بندی و پیشنهاد دسته و برچسب | ارزان | |
| تحلیل بروزرسانی محتوا | قوی | |
| استنباط فیلدهای پروفایل | متوسط | فقط یک بار در راه‌اندازی |

**پرامپت تصویر را کدام مدل بنویسد؟**

مدل تصویرساز پرامپت نمی‌نویسد؛ فقط پرامپت دریافت می‌کند. بهترین نویسنده پرامپت تصویر، مدلی است که مقاله را نوشته، چون کل محتوا را در اختیار دارد. بنابراین:

1. مدل نگارش مقاله در **همان پاسخ** برای هر Slot تصویر یک **بریف تصویر** تولید می‌کند: مفهوم، استعاره بصری، اجزای پیش‌زمینه و پس‌زمینه، حس و پالت رنگ، به‌همراه Alt فارسی. هزینه این کار فقط چند ده توکن خروجی بیشتر است.
2. در صورت نیاز، یک مدل ارزان بریف را به قالب و محدودیت‌های مدل تصویرساز انتخاب‌شده تبدیل می‌کند (طول، ترتیب اجزا، پارامترهای سبک). اگر قالب ثابت کافی باشد، این مرحله با Template و بدون هوش مصنوعی انجام می‌شود.
3. سبک بصری سایت (بخش 4.8.1) به‌صورت ثابت به انتهای هر پرامپت اضافه می‌شود تا تصاویر یکدست بمانند.
4. مدل تصویرساز فقط تصویر را تولید می‌کند.

**ترتیب اجرای کامل برای یک مقاله**

```text
1. تحقیق (در صورت نیاز)             مدل قوی + جستجو
2. نگارش مقاله + بریف تصاویر + Alt   مدل قوی، یک درخواست
3. اعتبارسنجی خروجی                 بدون هوش مصنوعی (Schema و قواعد)
4. تطبیق پرامپت تصاویر               Template یا مدل ارزان
5. تولید تصاویر                      مدل تصویرساز، Job جداگانه برای هر Slot
6. بهینه‌سازی و درج تصاویر          بدون هوش مصنوعی
7. ذخیره یا انتشار                   طبق سیاست انتشار
8. کپشن شبکه‌های اجتماعی             مدل ارزان، هنگام انتشار
```

**زنجیره جایگزین (Fallback)**

برای هر وظیفه یک مدل اصلی و حداکثر دو جایگزین تعریف می‌شود. در صورت خطا، Timeout، محدودیت نرخ یا قطع دسترسی، وظیفه با مدل بعدی ادامه پیدا می‌کند. اگر خروجی مدل ارزان از اعتبارسنجی Schema عبور نکند، یک بار با مدل سطح بالاتر تکرار می‌شود.

**پیش‌تنظیم‌ها (Presets)**

| پیش‌تنظیم | رفتار |
|---|---|
| اقتصادی | مدل متوسط برای نگارش، ارزان برای بقیه، Batch برای همه کارهای غیرفوری، حداقل تصویر |
| متعادل (پیش‌فرض) | جدول مسیریابی پیش‌فرض |
| کیفیت بالا | مدل قوی برای نگارش، تحلیل و توضیحات محصول؛ Alt با `vision` |
| سفارشی | انتخاب مدل برای هر وظیفه |

نزدیک شدن به سقف بودجه ماهانه می‌تواند به‌صورت خودکار پیش‌تنظیم را به «اقتصادی» تغییر دهد (قابل تنظیم).

نام مدل‌ها در کد ثابت نیست. فهرست مدل‌ها از Provider خوانده یا توسط مدیر وارد می‌شود، چون مدل‌ها و قیمت‌ها مرتباً تغییر می‌کنند.

ویژگی‌ها:

- ویرایش مسترپرامپت

### ساختار ترکیب Prompt

```text
Global Instructions
        +
Site Context
        +
Task Master Prompt
        +
Current Task Data
        |
        v
     AI Request
        |
        v
    Structured Response
```

اطلاعات سایت باید متناسب با وظیفه انتخاب شوند تا از ارسال اطلاعات غیرضروری و مصرف بی‌رویه توکن جلوگیری شود.

### نقش ContentMaster

| لایه | منبع |
|---|---|
| Global Instructions | هسته ContentMaster (قوانین عدم جعل اطلاعات، عدم تکرار، لینک‌دهی، کیفیت نگارش) |

| Task Master Prompt | PM-001 تا PM-006 به‌همراه ماژول صنعتی فعال (حقوقی، فروشگاهی، آموزشی، دایرکتوری، سفارشی) |
| Current Task Data | داده‌های همان وظیفه |

### Context Builder

Context Builder برای هر وظیفه فقط داده لازم را انتخاب می‌کند:

| وظیفه | داده ارسالی |
|---|---|
| Topic Research | پروفایل، دسته‌بندی‌ها، عنوان و کلمه کلیدی مقالات (بدون متن) |
| Article Writing | پروفایل، صفحات کلیدی، مقالات منتشرشده هم‌دسته و مرتبط (عنوان و آدرس) |
| Content Refresh | پروفایل، متن کامل همان مقاله، داده سرچ کنسول همان آدرس، مقالات مرتبط |
| Category Description | پروفایل، دسته‌بندی، عنوان مقالات یا محصولات آن دسته |

خروجی تمام وظایف به‌صورت JSON با Schema مشخص دریافت و قبل از ذخیره اعتبارسنجی می‌شود.

---

### ContentMaster به‌عنوان الگوی پیش‌فرض (جدید)

- ContentMaster همراه افزونه نصب می‌شود (`prompts/contentmaster-core.md` و ماژول‌های صنعتی در `prompts/industry-modules/`) و الگوی پیش‌فرض تمام وظایف تولید محتوا است.
- نسخه پیش‌فرض فقط‌خواندنی است. هر تغییر مدیر به‌صورت یک **نسخه سفارشی** جدا ذخیره می‌شود و نسخه پیش‌فرض دست‌نخورده می‌ماند.
- با بروزرسانی افزونه، اگر ContentMaster پیش‌فرض تغییر کند، نسخه‌های سفارشی بازنویسی نمی‌شوند. به مدیر اعلان «نسخه جدید پیش‌فرض موجود است» نمایش داده می‌شود، همراه با مقایسه تغییرات (Diff) و گزینه‌های «ادغام»، «جایگزینی» یا «نادیده گرفتن».
- بازگشت به نسخه پیش‌فرض در هر زمان ممکن است.

### لایه‌های تنظیمات محتوا (جدید)

شخصی‌سازی مستقیم متن مسترپرامپت در هر بار تولید، نظم محتوایی سایت را از بین می‌برد. به‌جای آن، شخصی‌سازی از طریق **متغیرهای تعریف‌شده** و در لایه‌های مشخص انجام می‌شود:

```text
لایه 0  قوانین هسته ContentMaster      قفل (فقط با بروزرسانی افزونه)
لایه 1  پیش‌فرض‌های سایت                تنظیمات محتوا + پروفایل سایت
لایه 2  تنظیمات دسته‌بندی               اختیاری، برای هر دسته
لایه 3  قالب محتوا (Content Template)   مانند راهنمای جامع، مقایسه، پاسخ کوتاه
لایه 4  تنظیمات همین تولید              فقط متغیرهای مجاز و در بازه مجاز
```

ترتیب اولویت: لایه 4، سپس 3، سپس 2، سپس 1. **قوانین لایه 0 در هیچ لایه‌ای قابل تغییر نیستند.**

#### لایه 0 – قوانین قفل‌شده (حافظ یکپارچگی)

این موارد در هیچ تولیدی قابل تغییر نیستند:

- عدم جعل اطلاعات، آمار، قانون، قیمت و منبع
- لینک داخلی فقط به آدرس‌های موجود، هر آدرس یک بار، قواعد انکرتکست
- یک نیت جستجوی غالب در هر مقاله
- ساختار HTML، تگ‌ها و کلاس‌های مجاز (`example-box`، `tip-box` و…)
- قواعد سرفصل‌ها (بدون H1، سلسله‌مراتب منطقی)
- قواعد فیلدهای سئو (طول عنوان و توضیحات متا، اسلاگ انگلیسی)
- قوانین ماژول صنعتی (مانند الزامات YMYL و سلب مسئولیت حقوقی)
- موضوعات ممنوع پروفایل
- قواعد نگارش فارسی (نیم‌فاصله، علائم نگارشی، یکدستی ارقام)
- ساختار پاسخ‌محور و پوشش نیاز کاربر (بخش 4.13.4 و بخش 6)
- صداقت در سناریوها و ناشناس‌سازی (بخش 4.12)

#### لایه 1 – پیش‌فرض‌های سایت (ثابت برای همه مقالات، حافظ هویت برند)

| تنظیم | توضیح |
|---|---|
| لحن مجاز | یک لحن اصلی و حداکثر 2 لحن جایگزین؛ لایه‌های بعدی فقط از همین فهرست انتخاب می‌کنند |
| واژه‌نامه برند | اصطلاحات ترجیحی و ممنوع (مثلاً «وکیل پایه یک دادگستری»، نام صحیح محصولات و خدمات) |
| سبک بصری تصاویر | ثابت برای همه تصاویر سایت |
| سبک CTA | لحن و نوع دعوت به اقدام |
| بازه‌های مجاز | حداقل و حداکثر هر متغیر لایه 4 (مثلاً تعداد کلمات بین 600 و 2500) |
| مقادیر پیش‌فرض | مقدار پیش‌فرض همه متغیرها |

#### لایه 2 – تنظیمات دسته‌بندی (اختیاری)

برای دسته‌هایی که نیاز متفاوتی دارند؛ مثلاً در سایت حقوقی، دسته «دعاوی کیفری» با حداقل کلمات بیشتر، بخش سوالات متداول اجباری و CTA «مشاوره فوری».

#### لایه 3 – قالب‌های محتوا (Content Templates)

هر قالب، مجموعه‌ای از مقادیر متغیرها و یک ساختار پیشنهادی است:

| قالب | ویژگی‌های پیش‌فرض |
|---|---|
| راهنمای جامع (Pillar) | 1800 تا 2500 کلمه، 6 تا 8 لینک داخلی، 3 تصویر داخلی، سوالات متداول، جدول مجاز |
| مقاله استاندارد | 900 تا 1200 کلمه، 3 تا 5 لینک، 2 تصویر |
| پاسخ کوتاه به یک سؤال | 500 تا 700 کلمه، 2 تا 3 لینک، 1 تصویر، پاسخ مستقیم در پاراگراف اول |
| مقایسه (X یا Y) | 1000 تا 1400 کلمه، جدول مقایسه اجباری، 2 تصویر |
| فهرستی (X روش / X نکته) | تعداد آیتم برابر عدد عنوان، 1 تا 3 تصویر |
| راهنمای قدم‌به‌قدم | فهرست شماره‌دار، 1 تصویر به ازای هر چند مرحله |
| خدمات محلی | تأکید بر منطقه جغرافیایی، لینک اجباری به صفحه خدمت و تماس |

قالب‌ها قابل ویرایش و افزودن هستند، نسخه‌بندی می‌شوند و در تحقیق موضوع، قالب مناسب هر موضوع پیشنهاد می‌شود.

#### لایه 4 – متغیرهای قابل شخصی‌سازی در هر تولید

| متغیر | نوع |
|---|---|
| قالب محتوا | انتخاب از فهرست |
| تعداد کلمات | بازه، در محدوده مجاز سایت |
| تعداد لینک داخلی | حداقل و حداکثر |
| حداقل لینک به صفحات کلیدی | عدد |
| صفحات کلیدی اجباری یا ممنوع برای این مقاله | انتخاب |
| تعداد تصاویر داخلی | عدد، در محدوده مجاز |
| حالت تصویر شاخص | از گزینه‌های بخش 4.8.1 |
| رویکرد آموزشی | مثال‌محور، مقایسه‌ای، موقعیت‌محور، قدم‌به‌قدم و… |
| لحن | فقط از لحن‌های مجاز سایت |
| سطح مخاطب | مبتدی / عمومی / حرفه‌ای |
| بخش سوالات متداول | خاموش / روشن و تعداد سؤال |
| جدول | مجاز / اجباری / ممنوع |
| CTA | انتخاب از CTAهای پروفایل |

| منطقه جغرافیایی | از محدوده پروفایل |

### اعتبارسنجی تنظیمات پیش از تولید

ترکیب‌های ناسازگار پیش از ارسال درخواست بررسی و هشدار داده می‌شوند:

- تعداد تصاویر زیاد نسبت به حجم متن (مثلاً بیش از یک تصویر به ازای هر 250 کلمه)
- تعداد لینک داخلی بیش از ظرفیت متن یا بیش از تعداد مقالات مرتبط موجود
- دستور تکمیلی متناقض با قوانین قفل‌شده یا موضوعات ممنوع
- قالب ناسازگار با نیت جستجوی موضوع

### پیش‌نمایش و Snapshot

- **پیش‌نمایش پرامپت نهایی:** امکان مشاهده پرامپت ترکیب‌شده، تعداد توکن و هزینه تخمینی پیش از اجرا (برای مدیران)
- **Generation Snapshot:** تنظیمات نهایی هر تولید (نسخه مسترپرامپت، قالب، مقادیر متغیرها، مدل و Provider) همراه محتوا ذخیره می‌شود. این کار تولید مجدد با همان تنظیمات، مقایسه نتایج و ردیابی علت کیفیت متفاوت را ممکن می‌کند.
- **ذخیره به‌عنوان قالب:** مجموعه تنظیماتی که برای یک تولید استفاده شده، قابل ذخیره به‌عنوان قالب جدید است.

## 4.5 Site Profile Builder (جدید)

هدف: مدیر سایت به‌جای پر کردن یک فرم طولانی، فقط اطلاعاتی را وارد کند که از سایت قابل استخراج نیست.

### منابع تکمیل فیلدها

| منبع | توضیح | نمونه |
|---|---|---|
| `detected` | مستقیماً از وردپرس خوانده می‌شود | نام سایت، دامنه، زبان، دسته‌بندی‌ها، صفحات، منوها، افزونه سئو، WooCommerce |
| `inferred` | با قواعد مشخص یا هوش مصنوعی پیشنهاد می‌شود | صفحات کلیدی، ماژول صنعتی، محدوده جغرافیایی، حساسیت محتوا |
| `manual` | فقط توسط مدیر وارد می‌شود | مخاطب، لحن، موضوعات ممنوع، قوانین اختصاصی، CTAها |

هر فیلد علاوه بر مقدار، `source` و `confirmed` دارد. فیلدهای `inferred` تا تأیید مدیر به‌عنوان پیشنهاد نمایش داده می‌شوند.

### قواعد استنباط در فاز 1 (بدون هوش مصنوعی)

- **صفحات کلیدی:** صفحات موجود در منوی اصلی و صفحاتی با اسلاگ یا عنوان شناخته‌شده (contact، about، services، pricing، consultation، booking، تماس، مشاوره، خدمات، تعرفه)
- **CTA:** صفحات تماس، رزرو و مشاوره، و فرم‌های شناسایی‌شده (Contact Form 7، WPForms، Gravity Forms)
- **ماژول صنعتی:** وجود WooCommerce (فروشگاهی)، کلمات شاخص در دسته‌بندی‌ها و عنوان سایت (حقوقی، آموزشی و…)
- **محدوده جغرافیایی:** تنظیمات Local SEO افزونه سئو، نام شهر یا منطقه در عنوان و توضیحات سایت
- **حساسیت محتوا:** ماژول حقوقی، پزشکی یا مالی، به‌معنای YMYL

از فاز 2، هوش مصنوعی می‌تواند با خواندن Inventory پیشنهادهای دقیق‌تری برای همین فیلدها و برای «محدوده موضوعی هر دسته» ارائه دهد.

### ویزارد راه‌اندازی

پس از اولین اسکن، یک ویزارد کوتاه نمایش داده می‌شود:

1. تأیید اطلاعات تشخیص‌داده‌شده
2. تأیید یا اصلاح صفحات کلیدی پیشنهادی (تیک صفحه کلیدی، «چه زمانی لینک شود»، انکرتکست‌های مجاز، اولویت)
3. تعیین محدوده موضوعی هر دسته‌بندی
4. انتخاب ماژول صنعتی و حساسیت محتوا
5. تکمیل فیلدهای دستی (مخاطب، لحن، CTA، موضوعات ممنوع)

ویزارد قابل رد شدن است. فیلدهای ناقص در فهرست `missing_fields` خروجی ثبت می‌شوند تا ContentMaster فقط همان‌ها را از کاربر بپرسد.

ساختار پروفایل باید با بخش SITE PROFILE در ContentMaster یک‌به‌یک قابل نگاشت باشد.

## 4.6 Health Audit Engine (جدید)

ممیزی قاعده‌محور که بدون هوش مصنوعی و بدون هزینه API اجرا می‌شود و پس از هر اسکن بروزرسانی می‌شود.

### 4.6.1 لینک داخلی و محتوای یتیم

| کد | بررسی | شدت |
|---|---|---|
| `ORPHAN_POST` | نوشته منتشرشده بدون هیچ لینک ورودی از محتوای منتشرشده دیگر | بالا |
| `ORPHAN_PAGE` | برگه منتشرشده بدون لینک ورودی از محتوا و بدون حضور در منو | بالا |
| `ORPHAN_PRODUCT` | محصول بدون لینک ورودی از مقالات (در صورت فعال بودن WooCommerce) | متوسط |
| `MENU_ONLY` | محتوایی که فقط از منو لینک گرفته و هیچ لینک درون‌متنی ندارد | کم |
| `WEAK_INBOUND` | محتوای مهم (صفحه کلیدی یا Cornerstone) با لینک ورودی کمتر از آستانه | متوسط |
| `NO_INTERNAL_LINKS` | محتوای بدون لینک خروجی داخلی | متوسط |
| `BROKEN_INTERNAL_LINK` | لینک به آدرس ناموجود یا ریدایرکت‌شده | بالا |

تعریف‌ها:
- لینک ورودی فقط از محتوای **منتشرشده** شمرده می‌شود؛ لینک از پیش‌نویس‌ها حساب نمی‌شود.
- لینک‌های منو، ابزارک‌ها و فوتر جداگانه ثبت می‌شوند و محتوا را از حالت یتیم خارج نمی‌کنند؛ فقط وضعیت `MENU_ONLY` را تعیین می‌کنند.
- برگه‌های سیستمی (سبد خرید، تسویه حساب، حساب کاربری، حریم خصوصی، تشکر) و محتوای noindex به‌صورت پیش‌فرض مستثنا هستند و فهرست استثناها قابل ویرایش است.

برای هر محتوای یتیم، 3 تا 5 مقاله مرتبط به‌عنوان منبع لینک پیشنهاد می‌شود: در فاز 1 بر اساس دسته‌بندی و برچسب مشترک، و از فاز 2 بر اساس شباهت معنایی (Embedding)، همراه با انکرتکست و جمله پیشنهادی. پیشنهادها در صف تأیید Internal Links قرار می‌گیرند.

### 4.6.2 محتوا و سئو

| کد | بررسی | شدت |
|---|---|---|
| `NO_FOCUS_KEYWORD` | بدون کلمه کلیدی اصلی | متوسط |
| `NO_META_DESCRIPTION` | بدون توضیحات متا | متوسط |
| `DUPLICATE_FOCUS_KEYWORD` | یک کلمه کلیدی برای چند محتوا (احتمال Cannibalization) | بالا |
| `OUTDATED_YEAR` | ذکر سال گذشته در عنوان یا متن | بالا |
| `THIN_CONTENT` | تعداد کلمات کمتر از آستانه تنظیم‌شده | متوسط |
| `NO_H2` | بدون ساختار سرفصل | کم |

بررسی‌های تصویر در بخش 4.8.4 تعریف شده‌اند.

### 4.6.3 سلامت دسته‌بندی و برچسب

| کد | بررسی | شدت |
|---|---|---|
| `EMPTY_CATEGORY` | دسته‌بندی بدون محتوای منتشرشده | متوسط |
| `WEAK_CATEGORY` | دسته‌بندی با محتوای کمتر از آستانه (پیش‌فرض: کمتر از 3) | متوسط |
| `EMPTY_CATEGORY_DESC` | دسته‌بندی بدون توضیحات یا با توضیحات کوتاه | متوسط |
| `SINGLE_CATEGORY_OVERLOAD` | تمرکز بیش از حد محتوا در یک دسته | متوسط |
| `MISCATEGORIZED` | محتوایی که موضوع آن با دسته‌بندی‌اش هم‌خوان نیست (فاز 2، با هوش مصنوعی) | متوسط |
| `SIMILAR_CATEGORIES` | دسته‌بندی‌های با نام یا محتوای بسیار مشابه | متوسط |
| `EMPTY_TAG` | برچسب بدون محتوا | کم |
| `THIN_TAG` | برچسب با فقط یک محتوا (آرشیو کم‌ارزش برای ایندکس) | کم |
| `NEAR_DUPLICATE_TAGS` | برچسب‌های تقریباً یکسان پس از نرمال‌سازی | کم |
| `TAG_EQUALS_CATEGORY` | برچسب هم‌نام با یک دسته‌بندی | کم |
| `TAG_OVERUSE` | تعداد برچسب بیش از حد برای یک محتوا | کم |
| `INDEXED_THIN_ARCHIVE` | آرشیو دسته یا برچسب ضعیف که noindex نیست | متوسط |

برای هر یافته یکی از اقدامات زیر پیشنهاد می‌شود: **ادغام** با دسته یا برچسب مشابه، **حذف**، **noindex**، **تولید محتوا** برای تقویت دسته (ارسال به برنامه محتوا)، یا **نوشتن توضیحات** (ارسال به Category Manager).

ادغام و حذف فقط پس از تأیید مدیر انجام می‌شوند، محتوای مرتبط به دسته یا برچسب مقصد منتقل می‌شود، و برای آدرس آرشیو حذف‌شده ریدایرکت 301 پیشنهاد می‌شود (در صورت وجود Rank Math یا افزونه Redirection، به‌صورت خودکار ثبت می‌شود).

### 4.6.4 شناسایی مقالات قدیمی برای بازنویسی (Refresh Candidates)

هر مقاله منتشرشده یک **امتیاز نیاز به بروزرسانی** (0 تا 100) دارد که از عوامل زیر محاسبه می‌شود:

| عامل | منبع |
|---|---|
| مدت زمان از آخرین ویرایش | تاریخ `modified` |
| ذکر سال یا ارقام زمان‌دار گذشته | `OUTDATED_YEAR` |
| محتوای کم‌حجم یا بدون ساختار | `THIN_CONTENT`، `NO_H2` |
| نبود پاسخ مستقیم در ابتدای مقاله | `NO_DIRECT_ANSWER` |
| لینک‌های داخلی کم یا شکسته | بخش 4.6.1 |
| تصاویر ناقص یا بدون Alt | بخش 4.8.4 |
| افت کلیک یا رتبه | داده Search Console (در صورت وجود) |
| فرصت نزدیک به صفحه اول | رتبه 8 تا 20 با نمایش بالا (در صورت وجود داده) |
| رقابت با مقاله دیگر سایت | `DUPLICATE_FOCUS_KEYWORD` |

برای هر مقاله یکی از اقدامات زیر پیشنهاد می‌شود:

| اقدام | زمان استفاده |
|---|---|
| بروزرسانی سبک | اصلاح سال‌ها و ارقام، افزودن لینک و تصویر، بهبود عنوان و توضیحات متا |
| بازنویسی | ساختار ضعیف یا ناسازگار با نیت جستجو؛ آدرس حفظ می‌شود |
| ادغام | دو مقاله با نیت یکسان؛ ادغام در مقاله قوی‌تر و ریدایرکت 301 |
| ریدایرکت یا noindex | مقاله بی‌ارزش یا منسوخ |

فهرست «پیشنهاد بازنویسی» بر اساس امتیاز و اثر احتمالی مرتب می‌شود و هر مورد با یک کلیک به Content Refresh ارسال می‌شود. بازنویسی همیشه آدرس مقاله را حفظ می‌کند (مگر در ادغام)، با Revision همراه است و تاریخ `modified` را بروز می‌کند.

آستانه‌ها در تنظیمات قابل تغییر هستند.

یافته‌ها در داشبورد با امکان فیلتر، علامت‌گذاری به‌عنوان «بررسی‌شده» و ارسال به چرخه Content Refresh نمایش داده می‌شوند.

## 4.7 Persian Text Normalizer (جدید)

سرویس مشترکی که پیش از هر مقایسه متنی (تشخیص تکرار، تطبیق کلمه کلیدی، تطبیق برچسب) اجرا می‌شود:

- یکسان‌سازی «ي» و «ی»، «ك» و «ک»
- یکسان‌سازی ارقام فارسی، عربی و لاتین
- یکسان‌سازی نیم‌فاصله، فاصله و حذف کشیده (ـ)
- حذف اعراب و علائم اضافه
- Decode اسلاگ‌های فارسی
- تشخیص سال‌های شمسی (۱۳۹۰ تا سال جاری) و میلادی

متن اصلی تغییر نمی‌کند و نرمال‌سازی فقط برای مقایسه و ایندکس انجام می‌شود.

## 4.8 Media & Image Module (جدید)

تصویر شاخص و تصاویر داخل متن بخش اصلی کیفیت مقاله هستند. این ماژول تولید، درج، بهینه‌سازی و ممیزی تصاویر را مدیریت می‌کند.

### 4.8.1 تنظیمات تصویر (قابل تنظیم در سطح سایت و قابل تغییر برای هر مقاله)

| تنظیم | گزینه‌ها |
|---|---|
| حالت تصویر شاخص | بدون تصویر / فقط پرامپت تصویر / تولید با هوش مصنوعی / انتخاب دستی از کتابخانه رسانه |
| حالت تصاویر داخل متن | بدون تصویر / فقط پرامپت / تولید با هوش مصنوعی / جای‌نگهدار برای افزودن دستی |
| تعداد تصاویر داخل متن | عدد ثابت (0 تا 6) یا نسبی (یک تصویر به ازای هر X کلمه)، با حداقل و حداکثر |
| محل قرارگیری | پس از مقدمه / پس از H2های منتخب / توزیع یکنواخت |
| نوع تصاویر داخل متن | مفهومی، صحنه کاربردی، مرحله‌ای، مقایسه‌ای، محصول در محیط واقعی |
| سبک بصری | از پروفایل سایت (Visual Style) با امکان Preset اختصاصی |
| اندازه و نسبت تصویر | جدول 4.8.1-ب |
| Image Provider | Adapter مستقل (مانند OpenAI، Google و سایر سرویس‌ها) |
| خروجی فایل | فرمت WebP، حداکثر عرض، کیفیت فشرده‌سازی |
| تأیید تصویر | تأیید دستی پیش از درج / درج خودکار |

**جدول 4.8.1-ب: اندازه تصاویر**

| نوع تصویر | اندازه پیش‌فرض (پیکسل) | قابل تنظیم |
|---|---|---|
| تصویر شاخص | 1200 × 675 (16:9) | عرض، ارتفاع، نسبت |
| تصویر داخل متن – افقی | 800 × 450 (16:9) | عرض، ارتفاع، نسبت |
| تصویر داخل متن – مربع | 800 × 800 (1:1) | عرض |
| تصویر شبکه‌های اجتماعی – مربع | 1080 × 1080 | عرض |
| تصویر شبکه‌های اجتماعی – عمودی | 1080 × 1350 (4:5) | عرض |
| Open Graph | 1200 × 630 | — |

تنظیمات تکمیلی:

- **تشخیص اندازه‌های قالب:** اندازه‌های ثبت‌شده توسط قالب فعال (مانند اندازه تصویر شاخص قالب) شناسایی و به‌عنوان پیش‌فرض پیشنهاد می‌شوند تا تصویر در قالب برش نخورد یا کشیده نشود.
- **حالت برش:** برش از مرکز / برش هوشمند از محل سوژه / بدون برش (تغییر اندازه با حفظ نسبت)
- **سقف حجم فایل:** مثلاً حداکثر 150 کیلوبایت برای شاخص و 100 کیلوبایت برای داخل متن؛ کیفیت فشرده‌سازی تا رسیدن به سقف به‌صورت خودکار تنظیم می‌شود.
- **اندازه تولید در برابر اندازه خروجی:** مدل‌های تصویرساز معمولاً اندازه‌های ثابتی تولید می‌کنند. تصویر در نزدیک‌ترین اندازه پشتیبانی‌شده با همان نسبت تولید و سپس دقیقاً به اندازه تعیین‌شده برش و تغییر اندازه داده می‌شود.
- **اندازه‌های واکنش‌گرا:** پس از ثبت در کتابخانه رسانه، اندازه‌های فرعی وردپرس ساخته می‌شوند تا srcset به‌درستی کار کند.
- **width و height:** همیشه در تگ تصویر درج می‌شوند تا از جابه‌جایی صفحه هنگام بارگذاری (CLS) جلوگیری شود.

### 4.8.2 روند تولید

1. مقاله با جای‌نگهدارهای تصویر تولید می‌شود: `<!-- paydarpress:image slot="2" -->`
2. برای هر Slot، پرامپت تصویر بر اساس سرفصل و پاراگراف همان بخش ساخته می‌شود.
3. تصویر در یک Job مستقل تولید می‌شود. خطای تولید تصویر مانع ذخیره مقاله نمی‌شود و فقط Slot در وضعیت «نیازمند تصویر» باقی می‌ماند.
4. فایل بهینه‌سازی می‌شود (WebP، تغییر اندازه) و با نام انگلیسی مبتنی بر اسلاگ مقاله ذخیره می‌شود (مثلاً `consensual-divorce-steps-2.webp`).
5. در کتابخانه رسانه با Alt، Title و Caption (اختیاری) ثبت و به مقاله متصل می‌شود.
6. پرامپت هر تصویر در Meta ذخیره می‌شود تا امکان تولید مجدد وجود داشته باشد.

### 4.8.3 قوانین

- تصاویر نباید حاوی متن باشند؛ مدل‌های تصویرساز متن فارسی را معمولاً نادرست رسم می‌کنند.
- بدون لوگو، برند واقعی یا چهره افراد واقعی.
- برای سایت‌های فروشگاهی، تصویر هوش مصنوعی جایگزین عکس واقعی محصول نمی‌شود و فقط برای تصاویر مفهومی مقالات استفاده می‌شود.
- هزینه تخمینی تصاویر پیش از اجرا نمایش داده می‌شود و در سقف بودجه ماهانه محاسبه می‌شود.

### 4.8.4 ممیزی و بهبود تصاویر موجود

| کد | بررسی |
|---|---|
| `IMG_MISSING_ALT` | تصویر شاخص یا داخل متن بدون Alt |
| `IMG_GENERIC_ALT` | Alt بی‌معنا: نام فایل، `IMG_1234`، «تصویر»، «image» |
| `IMG_DUPLICATE_ALT` | Alt یکسان برای تصاویر متفاوت |
| `IMG_ALT_KEYWORD_STUFFING` | Alt طولانی یا پر از کلمه کلیدی |
| `IMG_NO_FEATURED` | مقاله بدون تصویر شاخص |
| `IMG_NO_INLINE` | مقاله طولانی بدون تصویر داخل متن (آستانه قابل تنظیم) |
| `IMG_OVERSIZED` | حجم یا ابعاد بیش از حد |
| `IMG_LEGACY_FORMAT` | فرمت غیر WebP/AVIF |
| `IMG_NO_DIMENSIONS` | تصویر داخل متن بدون width و height |
| `IMG_BAD_FILENAME` | نام فایل نامفهوم یا فارسی URL-encoded |

**تولید Alt برای تصاویر موجود** در دو روش:

1. **مبتنی بر متن (کم‌هزینه، پیش‌فرض):** از عنوان مقاله، سرفصل و پاراگراف اطراف تصویر و Caption موجود
2. **مبتنی بر تصویر (دقیق‌تر):** ارسال نسخه کوچک‌شده تصویر به مدل دارای قابلیت بینایی

**اعمال تغییرات:**
- Alt در دو محل ذخیره می‌شود: فیلد Alt فایل در کتابخانه رسانه (`_wp_attachment_image_alt`) و ویژگی `alt` داخل محتوای مقاله (بلوک Gutenberg، HTML کلاسیک یا داده Elementor). هر دو باید بروزرسانی شوند.
- پیشنهادها به‌صورت گروهی نمایش داده می‌شوند و پس از تأیید مدیر، همراه با Revision اعمال می‌شوند.
- تبدیل فرمت و فشرده‌سازی فقط با تأیید مدیر و با حفظ نسخه اصلی انجام می‌شود.

## 4.9 Token & Cost Optimization (جدید)

| روش | توضیح |
|---|---|
| Context Builder | ارسال فقط داده لازم هر وظیفه (بخش 4.4) |
| ادغام درخواست‌ها | بریف تصاویر و Alt در همان درخواست نگارش مقاله تولید می‌شوند، نه در درخواست جداگانه |
| Outline به‌جای متن کامل | متن کامل فقط در وظایفی ارسال می‌شود که به آن نیاز دارند (Content Refresh) |
| Prompt Caching | ترتیب ثابت پرامپت: هسته ContentMaster، سپس پروفایل سایت، سپس داده متغیر وظیفه. بخش ثابت در Providerهای پشتیبانی‌کننده کش می‌شود |
| Batch API | تولیدهای زمان‌بندی‌شده و غیرفوری (مقالات، توضیحات دسته‌بندی، Alt گروهی) در صورت پشتیبانی Provider به‌صورت Batch و با هزینه کمتر ارسال می‌شوند |

| Embedding | تشخیص تکرار و یافتن مقالات مرتبط با بردارهای ذخیره‌شده، به‌جای ارسال فهرست کامل مقالات به مدل |
| Rule-based First | هر بررسی قابل انجام با قاعده (Health Audit) بدون هوش مصنوعی انجام می‌شود |
| Cache پاسخ | نتایج تحقیق وب و تحلیل‌ها برای مدت مشخص ذخیره و دوباره استفاده می‌شوند |
| خروجی ساختاریافته کوتاه | درخواست خروجی JSON بدون توضیحات اضافه |
| بودجه | سقف ماهانه، سقف هر Job، تخمین هزینه پیش از اجرا و توقف خودکار در صورت عبور از سقف |

مصرف هر درخواست (توکن ورودی، خروجی، کش‌شده و هزینه) در `paydarpress_usage` ثبت و در ویجت «مصرف و هزینه» نمایش داده می‌شود.


## 4.10 Distribution Module – انتشار در پیام‌رسان‌ها و شبکه‌های اجتماعی (جدید)

هدف: پس از انتشار مقاله یا محصول در سایت، به‌صورت خودکار یا با تأیید مدیر، یک پست متناسب با هر کانال ارسال شود.

### 4.10.1 کانال‌ها

| کانال | روش اتصال | اولویت |
|---|---|---|
| بله | Bot API (مشابه تلگرام)؛ ربات باید مدیر کانال باشد | فاز اول توزیع |
| ایتا | API ایتایار با توکن کانال | فاز اول توزیع |
| روبیکا | Bot API روبیکا؛ ربات باید مدیر کانال باشد | فاز اول توزیع |
| تلگرام | Telegram Bot API؛ ربات باید مدیر کانال باشد | فاز اول توزیع |
| Webhook عمومی | ارسال JSON رویداد به هر آدرس (مانند n8n، Make یا سیستم اختصاصی) | فاز اول توزیع |
| اینستاگرام | تولید کپشن و تصویر مربعی برای انتشار دستی؛ انتشار خودکار از طریق API رسمی Meta فقط در صورت امکان دسترسی | بعدی |
| لینکدین و X | Adapter اختصاصی | بعدی |
| اعلان وب (Web Push) | Adapter برای سرویس‌های داخلی و خارجی Push | بعدی |
| خبرنامه ایمیلی | Adapter برای سرویس ارسال ایمیل | بعدی |

هر کانال یک Adapter مستقل در پوشه `channels/` دارد و افزودن کانال جدید نیازی به تغییر هسته ندارد. API هر کانال پیش از پیاده‌سازی باید از مستندات رسمی همان سرویس بررسی شود، چون این سرویس‌ها ممکن است تغییر کنند.

### 4.10.2 رویدادهای ارسال

| رویداد | توضیح |
|---|---|
| انتشار مقاله | از طریق Hook تغییر وضعیت به `publish` (فقط اولین انتشار، نه هر بار بروزرسانی) |
| انتشار محصول | در صورت فعال بودن WooCommerce |
| بروزرسانی مهم | اختیاری: ارسال مجدد فقط با انتخاب دستی مدیر |
| ارسال دستی | دکمه «ارسال به شبکه‌ها» در فهرست نوشته‌ها و صفحه ویرایش |
| بازنشر برنامه‌ریزی‌شده | اختیاری: بازنشر مقالات Evergreen قدیمی در بازه‌های تعیین‌شده |

قوانین هر کانال قابل تنظیم است: نوع محتوا (مقاله، محصول یا هر دو)، دسته‌بندی‌های مجاز یا مستثنا، و حالت **ارسال خودکار** یا **ارسال پس از تأیید**.

### 4.10.3 محتوای پست

- **قالب پست** برای هر کانال با متغیرها: `{title}`، `{excerpt}`، `{url}`، `{category}`، `{tags}`، `{price}`، `{site_name}`
- **کپشن هوش مصنوعی (اختیاری):** متن کوتاه و متناسب با لحن و محدودیت طول هر کانال، بر اساس خلاصه مقاله، با هزینه کم (مدل ارزان)
- **تصویر:** تصویر شاخص با اندازه مناسب هر کانال (بخش 4.8.1)
- **لینک:** همراه با پارامترهای UTM اختصاصی هر کانال، برای اندازه‌گیری ترافیک ورودی از هر شبکه
- **هشتگ:** از برچسب‌ها یا دسته‌بندی، با سقف تعداد
- **دکمه زیر پست** (در کانال‌هایی که پشتیبانی می‌کنند): «مطالعه مقاله» یا «مشاهده محصول»

### 4.10.4 اجرا و قابلیت اطمینان

- ارسال همیشه در **صف پس‌زمینه** انجام می‌شود. انتشار مقاله هرگز منتظر پاسخ شبکه‌های اجتماعی نمی‌ماند.
- امکان تعیین **تأخیر** پس از انتشار (مثلاً 10 دقیقه) تا فرصت اصلاح خطاهای لحظه آخر وجود داشته باشد.
- **فاصله ارسال** بین کانال‌ها و رعایت محدودیت نرخ هر سرویس
- **جلوگیری از ارسال تکراری:** هر محتوا برای هر کانال فقط یک بار ارسال می‌شود، مگر با ارسال مجدد دستی.
- **Retry** برای خطاهای موقت و ثبت خطای دائمی (توکن نامعتبر، ربات حذف‌شده از کانال) با اعلان به مدیر
- **ثبت سابقه:** شناسه پیام در هر کانال، زمان ارسال و وضعیت، در جدول `paydarpress_distribution_log`
- **دسترسی شبکه:** تلگرام معمولاً از هاست‌های داخل ایران در دسترس نیست و به Relay نیاز دارد (بخش 4.3). سرویس‌های داخلی ممکن است از هاست‌های خارج از ایران محدودیت داشته باشند. وضعیت اتصال هر کانال در تنظیمات با دکمه «تست اتصال» بررسی می‌شود.

### 4.10.5 سایر یکپارچه‌سازی‌ها

| یکپارچه‌سازی | کاربرد |
|---|---|
| IndexNow | اطلاع‌رسانی فوری انتشار یا بروزرسانی به موتورهای جستجوی پشتیبانی‌کننده (مانند Bing و Yandex) |
| Google Search Console | داده عملکرد برای ممیزی و بروزرسانی (بخش 10.6 و فاز 6) |
| Google Analytics 4 / Microsoft Clarity | نمایش بازدید و رفتار کاربر کنار هر مقاله در فهرست محتوا (فقط خواندن) |
| سامانه پیامک (Adapter برای سرویس‌دهندگان داخلی) | اعلان به مدیر: موضوعات منتظر تأیید، خطای صف، عبور از سقف بودجه |
| اعلان ایمیلی مدیر | گزارش هفتگی سلامت محتوا و فعالیت‌ها |
| ربات مدیریتی در بله یا تلگرام | دریافت اعلان و تأیید یا رد موضوعات از داخل پیام‌رسان (فاز بعدی) |
| Webhook خروجی برای همه رویدادها | اتصال به هر ابزار دیگر بدون توسعه Adapter جدید |


## 4.11 Authors & Expertise – نویسندگان و اعتبار تخصصی (جدید)

هدف: هر مقاله به یک نویسنده واقعی سایت نسبت داده شود و اعتبار تخصصی او برای کاربر، گوگل و هوش مصنوعی قابل تشخیص باشد.

### پروفایل نویسنده

برای هر کاربر وردپرس با نقش نویسندگی، فیلدهای زیر در User Meta (`_paydarpress_author_*`) نگهداری می‌شود:

| فیلد | توضیح |
|---|---|
| حوزه‌های تخصص | انتخاب از دسته‌بندی‌های سایت |
| عنوان تخصصی | مانند «وکیل پایه یک دادگستری»، «کارشناس تصفیه آب» |
| سابقه و مدارک | متن کوتاه، شماره پروانه یا عضویت (اختیاری، فقط در صورت تمایل) |
| بیوگرافی | برای صفحه نویسنده و باکس انتهای مقاله |
| لینک‌های معتبر | صفحات اجتماعی یا حرفه‌ای (برای `sameAs` در Schema) |
| نقش | نویسنده / بازبین تخصصی / هر دو |

### تخصیص نویسنده

| حالت | رفتار |
|---|---|
| دستی | مدیر هنگام تأیید موضوع یا پیش از تولید، نویسنده را انتخاب می‌کند |
| بر اساس دسته‌بندی | هر دسته یک نویسنده پیش‌فرض دارد |
| بر اساس تخصص | نویسنده‌ای که حوزه تخصصش با دسته مقاله منطبق است پیشنهاد می‌شود؛ در صورت چند گزینه، توزیع متوازن |
| نویسنده پیش‌فرض سایت | در صورت نبود قاعده دیگر |

- برای سایت‌های YMYL، فیلد **«بازبینی تخصصی توسط»** فعال است و نام و عنوان بازبین در انتهای مقاله و در Schema درج می‌شود.
- افزونه هرگز نویسنده یا مدرک ساختگی ایجاد نمی‌کند. فقط کاربران واقعی سایت قابل انتخاب هستند.
- نام و تخصص نویسنده در Context درخواست نگارش قرار می‌گیرد تا زاویه دید متن با تخصص نویسنده هم‌خوان باشد (بدون ادعای تجربه‌ای که نویسنده نداشته است).

### ممیزی نویسندگان

| کد | بررسی |
|---|---|
| `AUTHOR_NO_BIO` | نویسنده بدون بیوگرافی یا عنوان تخصصی |
| `AUTHOR_PAGE_THIN` | صفحه آرشیو نویسنده بدون معرفی |
| `YMYL_NO_REVIEWER` | مقاله YMYL بدون بازبین تخصصی |
| `ADMIN_AS_AUTHOR` | مقالات منتشرشده با کاربر admin یا نام عمومی |

## 4.12 Idea Inbox & Scenario Studio – ایده‌ها و سناریونویسی (جدید)

هدف: مدیر یا کارشناس بتواند خوراک اولیه (ایده، تجربه، یک پاراگراف، یادداشت یا یک پرونده واقعی) بدهد و هوش مصنوعی از آن مقاله‌ای مبتنی بر سناریو بسازد. این همان «اطلاعات اختصاصی» است که مقاله را از محتوای عمومی متمایز می‌کند.

### صندوق ایده (Idea Inbox)

انواع ورودی:

| نوع | نمونه |
|---|---|
| ایده | «درباره اینکه چرا بعضی طلاق‌های توافقی طولانی می‌شوند بنویسیم» |
| تجربه یا پرونده | «موکلی داشتیم که مهریه‌اش را به اقساط گرفت، ولی همسرش...» |
| یادداشت تخصصی | نکات فنی، اعداد و مراحل از تجربه کارگاه یا دفتر |
| سؤال واقعی مشتری | سؤالی که مشتریان مکرر می‌پرسند |
| متن پیاده‌شده از صدا | متن یک فایل صوتی که مدیر ضبط کرده |

هر ایده دسته‌بندی، برچسب «محرمانه / قابل استفاده»، و نوع استفاده (سناریو اصلی، مثال داخل مقاله، فقط الهام) دارد. ایده‌ها در تحقیق موضوع (PM-001) هم به‌عنوان ورودی استفاده می‌شوند.

### روند سناریونویسی

```text
ورودی (پاراگراف یا ایده)
      |
      v
تحلیل: نیت جستجو، موضوع قابل‌جستجو، دسته‌بندی، تکراری نبودن
      |
      v
پیش‌نویس سناریو (Scenario Draft)
  - شخصیت (پرسونا، بدون مشخصات واقعی)
  - موقعیت و مسئله
  - تصمیم‌ها و گره‌ها
  - مراحل حل و نتیجه
  - درس‌ها و نکات قابل تعمیم
  - عنوان و کلمه کلیدی پیشنهادی
      |
      v
تأیید یا ویرایش توسط مدیر
      |
      v
تولید مقاله با رویکرد Story-based یا Situation-based
```

### قوانین سناریو

- **ناشناس‌سازی:** نام، شهر کوچک، تاریخ دقیق، مبالغ و هر جزئیات قابل شناسایی از پرونده‌های واقعی حذف یا تعمیم داده می‌شود. ورودی‌های دارای برچسب «محرمانه» هرگز مستقیم نقل نمی‌شوند.
- **صداقت:** سناریوی ساخته‌شده توسط هوش مصنوعی با عبارتی مانند «فرض کنید…» یا «یک نمونه رایج…» معرفی می‌شود و به‌عنوان رویداد واقعی ارائه نمی‌شود. فقط سناریوهای برگرفته از ورودی واقعی می‌توانند «تجربه واقعی» نامیده شوند.
- **وفاداری به ورودی:** اعداد، مراحل و نکات تخصصی ورودی بدون تغییر حفظ می‌شوند و هوش مصنوعی جزئیات فنی به آن اضافه نمی‌کند، مگر با منبع.
- سناریو در خدمت پاسخ به نیاز کاربر است و جایگزین پاسخ مستقیم نمی‌شود.

## 4.13 AI Visibility & Crawlability – دیده‌شدن در گوگل و هوش مصنوعی (جدید)

### 4.13.1 معرفی به موتورهای جستجو

| روش | توضیح |
|---|---|
| نقشه سایت | بررسی وجود و سلامت نقشه سایت افزونه سئو و حضور مقالات جدید در آن |
| ارسال نقشه سایت به Search Console | از طریق Search Console API پس از اتصال (فاز 6) |
| IndexNow | اطلاع‌رسانی فوری انتشار و بروزرسانی به موتورهای پشتیبانی‌کننده (بخش 4.10.5) |
| لینک داخلی از صفحات پربازدید | مقاله جدید از چند صفحه قدیمی و پربازدید لینک می‌گیرد (صف لینک‌های معکوس) |

یادداشت: Google Indexing API فقط برای انواع محدودی از محتوا (مانند آگهی شغلی) مجاز است و برای مقالات استفاده نمی‌شود. روش قدیمی Ping نقشه سایت نیز دیگر توسط گوگل پشتیبانی نمی‌شود.

### 4.13.2 دسترسی خزنده‌ها (Crawler Access Check)

خزنده‌های هوش مصنوعی روش «ثبت» ندارند؛ فقط باید بتوانند سایت را ببینند. این بخش موانع را شناسایی می‌کند:

| بررسی | توضیح |
|---|---|
| robots.txt | آیا خزنده‌های گوگل، Bing و خزنده‌های هوش مصنوعی رایج (مانند GPTBot، OAI-SearchBot، ClaudeBot، PerplexityBot، Google-Extended) مسدود شده‌اند؟ وضعیت هر کدام با توضیح اثر آن نمایش داده می‌شود و مدیر برای هر خزنده تصمیم می‌گیرد |
| دسترسی از خارج ایران | آیا سایت از خارج کشور باز می‌شود؟ بسیاری از هاست‌های داخلی ترافیک خارجی را محدود می‌کنند و خزنده‌ها از خارج می‌آیند. بررسی از طریق یک سرویس بررسی خارجی یا Relay انجام می‌شود |
| فایروال و CDN | هشدار درباره تنظیمات مسدودسازی ربات‌ها در Cloudflare و فایروال‌های امنیتی |
| محتوای قابل خواندن | آیا متن اصلی در HTML اولیه وجود دارد یا فقط با JavaScript ساخته می‌شود؟ |
| noindex و canonical نادرست | صفحات مهمی که به اشتباه از ایندکس خارج شده‌اند |
| llms.txt (اختیاری) | امکان ساخت خودکار؛ اثر آن بر ارجاع هوش مصنوعی اثبات نشده و در رابط کاربری همین‌طور توضیح داده می‌شود |

### 4.13.3 داده ساختاریافته (Schema)

اصل: **مدل هوش مصنوعی کد JSON-LD را داخل متن مقاله نمی‌نویسد.** مدل داده ساختاریافته (مانند سؤال و جواب‌ها) را به‌صورت فیلدهای JSON در خروجی برمی‌گرداند و پایدارپرس Schema را تولید و درج می‌کند. این کار از خطای نحوی، تکرار Schema و ناسازگاری با افزونه سئو جلوگیری می‌کند.

| نوع | منبع داده | توضیح |
|---|---|---|
| Article / BlogPosting | مقاله، نویسنده، تاریخ‌ها | همراه با `author` و `reviewedBy` |
| Person | پروفایل نویسنده (بخش 4.11) | با `jobTitle` و `sameAs` |
| Organization / LocalBusiness / LegalService | پروفایل سایت | نوع بر اساس ماژول صنعتی |
| FAQPage | بخش سوالات متداول مقاله | فقط وقتی سؤال‌ها در متن قابل مشاهده‌اند |
| BreadcrumbList | ساختار دسته‌بندی | معمولاً توسط افزونه سئو |
| Product | WooCommerce | معمولاً توسط WooCommerce یا افزونه سئو |

قوانین:
- **ادغام با افزونه سئو:** اگر Yoast یا Rank Math فعال باشد، داده‌ها از طریق APIهای Schema همان افزونه به گراف آن اضافه می‌شوند. اگر افزونه سئو نباشد، پایدارپرس JSON-LD را خودش درج می‌کند. هیچ نوع Schema دو بار درج نمی‌شود.
- Schema فقط محتوایی را توصیف می‌کند که در صفحه برای کاربر قابل مشاهده است.
- نمایش Rich Result برای برخی انواع (مانند FAQ) توسط گوگل محدود شده است. ارزش اصلی این داده‌ها خوانایی ماشینی و درک بهتر محتوا توسط موتورهای جستجو و هوش مصنوعی است، نه تضمین نمایش ویژه.
- اعتبارسنجی نحوی Schema پیش از درج انجام می‌شود.

### 4.13.4 ساختار پاسخ‌محور (Answer-First)

این قانون به لایه 0 (قوانین قفل‌شده) اضافه می‌شود:

- پاسخ مستقیم به سؤال اصلی مقاله در **40 تا 70 کلمه** و در ابتدای مقاله (پس از حداکثر یک جمله مقدمه)
- سرفصل‌ها در صورت امکان به شکل سؤالات واقعی کاربر
- هر بخش با پاسخ شروع می‌شود و سپس جزئیات می‌آید
- تعریف پیش از جزئیات، ادعای مشخص به‌جای کلی‌گویی

اعتبارسنجی پس از تولید، وجود پاراگراف پاسخ مستقیم را بررسی می‌کند (`NO_DIRECT_ANSWER`). همین بررسی در ممیزی مقالات قدیمی نیز اجرا می‌شود.

### 4.13.5 برنامه‌ریزی خوشه‌های موضوعی (Pillar & Cluster)

- هر دسته می‌تواند یک یا چند **مقاله ستون (Pillar)** داشته باشد. مقالات Cornerstone افزونه سئو به‌عنوان Pillar شناسایی می‌شوند.
- نقشه خوشه هر دسته نمایش داده می‌شود: Pillar، مقالات فرعی موجود، مقالات فرعی پیشنهادی، و لینک‌های موجود یا مفقود بین آن‌ها.
- **درصد پوشش خوشه:** نسبت زیرموضوعات پوشش داده‌شده به زیرموضوعات شناسایی‌شده در تحقیق
- تحقیق موضوع (PM-001) اولویت را به تکمیل خوشه‌های نیمه‌کامل می‌دهد، نه شروع خوشه‌های جدید.
- قواعد لینک: هر مقاله فرعی به Pillar لینک می‌دهد و Pillar به همه مقالات فرعی لینک می‌دهد.

### 4.13.6 پیگیری دیده‌شدن در هوش مصنوعی (اختیاری)

- مدیر فهرستی از **سؤالات آزمایشی** تعریف می‌کند (سؤالاتی که مخاطب از هوش مصنوعی می‌پرسد).
- در بازه‌های تعیین‌شده (مثلاً ماهانه)، سؤالات از طریق Providerهای دارای `web_search` پرسیده می‌شوند و ثبت می‌شود که آیا سایت به‌عنوان منبع آمده یا نام برند ذکر شده است.
- نتیجه در یک گزارش روند نمایش داده می‌شود.
- این قابلیت هزینه API دارد، پیش‌فرض خاموش است و تعداد سؤالات و دفعات آن محدود است. نتایج مدل‌ها متغیر است و به‌عنوان نشانه روند تفسیر می‌شود، نه عدد دقیق.

### سیاست انتشار

|---|---|---|

### بریف نیاز کاربر (User Need Brief)

پیش از نگارش هر مقاله، یک بریف کوتاه تولید و همراه درخواست نگارش ارسال می‌شود (در همان درخواست نگارش یا با مدل ارزان):

- سؤال اصلی کاربر (یک جمله)
- 3 تا 7 سؤال فرعی واقعی (از تحقیق، جستجوهای مرتبط و پرسش‌های رایج)
- کاربر پس از خواندن مقاله باید چه کاری را بتواند انجام دهد یا چه تصمیمی بگیرد
- نگرانی‌ها و ابهام‌های رایج
- قدم بعدی منطقی (اتصال به CTA)

پس از نگارش، اعتبارسنجی **پوشش نیاز** بررسی می‌کند که سؤال اصلی در ابتدای مقاله پاسخ داده شده و هر سؤال فرعی در متن یا بخش سوالات متداول پوشش داده شده باشد. موارد پوشش‌داده‌نشده در گزارش تولید ثبت می‌شوند.

### چک‌لیست اعتبارسنجی

انتشار (در هر سیاستی) فقط زمانی انجام شود که:

- تولید محتوا موفق باشد.
- ساختار خروجی با Schema مطابقت داشته باشد.
- محتوای ناقص نباشد (حداقل طول، وجود H2، وجود نتیجه‌گیری).
- HTML فقط شامل تگ‌های مجاز باشد.
- تمام لینک‌های داخلی به آدرس‌های موجود و منتشرشده اشاره کنند و هیچ آدرس ساختگی وجود نداشته باشد.
- هر آدرس فقط یک بار لینک شده باشد.
- موضوع با محتوای منتشرشده تکراری نباشد.
- موضوع در فهرست موضوعات ممنوع پروفایل نباشد.
- پاسخ مستقیم در ابتدای مقاله وجود داشته باشد و سؤالات بریف نیاز کاربر پوشش داده شده باشند.
- داده‌های Schema (مانند سوالات متداول) با متن قابل مشاهده منطبق باشند.
- نویسنده تعیین شده باشد و برای سایت‌های YMYL بازبین تخصصی تعیین شده باشد (یا مقاله فقط پیش‌نویس بماند).
- دسته‌بندی، برچسب‌ها و اطلاعات سئو معتبر باشند (طول عنوان و توضیحات متا، اسلاگ یکتا).
- عملیات ذخیره‌سازی موفق باشد.
- زمان انتشار فرا رسیده باشد.

در صورت بروز خطای اساسی، محتوا منتشر نمی‌شود و عملیات برای بررسی ثبت خواهد شد.

### لینک‌های معکوس

پس از ذخیره هر مقاله، 2 تا 3 مقاله منتشرشده مرتبط که باید به مقاله جدید لینک دهند، همراه با انکرتکست و جمله پیشنهادی، در صف تأیید Internal Links قرار می‌گیرند.

اعمال این لینک‌ها در مقالات قدیمی فقط پس از تأیید مدیر و با ثبت نسخه قبلی (Revision) انجام می‌شود.

|---|---|---|
| `contentmaster-lite` | استفاده در Claude و سایر چت‌ها | پروفایل، Taxonomyها، صفحات، مقالات (بدون متن کامل، با Outline و خلاصه)، خلاصه لینک‌ها، آمار، یافته‌های ممیزی |
| `full` | پشتیبان‌گیری و تحلیل کامل | همه بخش‌ها، شامل گراف کامل لینک و Media Inventory؛ متن کامل به‌صورت اختیاری |
| `custom` | خروجی انتخابی | بخش‌ها و نوع محتوای انتخاب‌شده توسط مدیر |

پروفایل `contentmaster-lite` برای سایتی با حدود 100 مقاله باید در حد چند صد کیلوبایت بماند.

برای سایت‌های بزرگ، خروجی به چند Part تقسیم می‌شود (`part` و `total_parts` در `export_meta`) یا فقط تغییرات پس از آخرین خروجی ارائه می‌شود (`since`).

### 10.4 ساختار سطح بالای Site Inventory

```text
export_meta    نسخه Schema، تاریخ، پروفایل خروجی، بخش‌ها، Part، افزونه سئو، صفحه‌ساز
site           اطلاعات عمومی سایت
profile        پروفایل سایت با source و confirmed برای هر فیلد، و missing_fields
taxonomies     categories، tags، product_categories و Taxonomyهای سفارشی
pages          صفحات با وضعیت حضور در منو
posts          مقالات با seo، content_stats، links_summary و flags
products       محصولات (در صورت فعال بودن WooCommerce)
links          گراف لینک داخلی (در پروفایل full)
stats          آمار کلی
warnings       هشدارها و یافته‌های ممیزی
data_coverage  بخش‌های موجود، ناقص یا حذف‌شده
```

نمونه کامل در فایل `paydarpress-site-inventory.example.json` ارائه شده است.

### 10.5 ContentMaster Import (جدید)

پایدارپرس فایل JSON خروجی ContentMaster را دریافت و پردازش می‌کند:

| نوع ورودی | عملیات |
|---|---|
| `topics` | ثبت در Suggested Topics |
| `articles` | ایجاد پیش‌نویس با عنوان، محتوا، دسته‌بندی، برچسب‌ها، اطلاعات سئو، اسلاگ و Alt |
| `link_suggestions` | ثبت در صف تأیید Internal Links |
| `refresh` | ثبت پیشنهادهای بروزرسانی برای مقاله مشخص، به‌صورت پیش‌نویس یا Revision |

این قابلیت پیش از اتصال API امکان استفاده از کل چرخه را فراهم می‌کند: خروجی از افزونه، پردازش در ContentMaster، و ورود نتایج به افزونه.

### 10.6 Search Console Import (جدید)

پیش از اتصال مستقیم به Google Search Console (فاز 6)، امکان ورود فایل CSV خروجی گزارش Performance (Pages و Queries) فراهم می‌شود.

داده‌ها به آدرس‌های Inventory متصل شده و در Content Refresh و Health Audit استفاده می‌شوند.

### الزامات طراحی دیتابیس

- استفاده از Primary Key مستقل
- ایجاد Index برای فیلدهای پرتکرار
- ذخیره JSON در فیلدهای مناسب
- پشتیبانی از Migration
- عدم وابستگی به ساختار داخلی جداول افزونه‌های دیگر
- ثبت نسخه Schema دیتابیس

نام‌گذاری جداول باید با Prefix استاندارد وردپرس نصب‌شده انجام شود و نام ثابت `wp_` در کد استفاده نشود.

Prefix اختصاصی پایدارپرس `paydarpress_` است (نه `paydar_`) تا با جداول سایر محصولات PaydarWP تداخل نداشته باشد (بخش 2.11). در این سند `wp_` فقط برای نمایش آمده است.

# 12. رابط کاربری و تجربه کاربری (UI / UX)

## 12.1 جایگاه در منوی وردپرس

منوی پیشخوان وردپرس فقط دو سطح دارد. بنابراین ساختار زیر استفاده می‌شود:

```text
پایدار وردپرس                 (منوی سطح اول مشترک همه محصولات PaydarWP)
├── پایدارپرس                 (اپلیکیشن تک‌صفحه‌ای با ناوبری داخلی)
├── [سایر محصولات PaydarWP]   (مانند پایدار کارت، هدر و فوتر)
└── لایسنس و بروزرسانی
```

- منوی «پایدار وردپرس» توسط کتابخانه مشترک PaydarWP Hub ثبت می‌شود (بخش 2.11). هر محصولی که زودتر بارگذاری شود منو را می‌سازد و بقیه فقط زیرمنوی خود را اضافه می‌کنند.
- تمام بخش‌های پایدارپرس داخل یک صفحه و با ناوبری داخلی (سایدبار سمت راست) نمایش داده می‌شوند.
- هر بخش آدرس مستقل دارد (`admin.php?page=paydarpress#/audit`) تا قابل بوکمارک و ارسال لینک باشد.

## 12.2 ناوبری داخلی (ترتیب بر اساس مسیر کار کاربر)

```text
پایدارپرس
│
├── پیشخوان
│
├── شناخت سایت
│   ├── پروفایل سایت
│   ├── فهرست محتوا
│   ├── دسته‌بندی‌ها و برچسب‌ها
│   ├── نویسندگان
│   └── رسانه‌ها
│
├── سلامت محتوا
│   ├── ممیزی
│   ├── محتوای یتیم و لینک‌های داخلی
│   ├── سلامت دسته‌بندی و برچسب
│   ├── سلامت تصاویر
│   ├── پیشنهاد بازنویسی
│   ├── دیده‌شدن در گوگل و هوش مصنوعی
│   └── بروزرسانی محتوا
│
├── برنامه محتوا
│   ├── صندوق ایده و سناریونویسی
│   ├── خوشه‌های موضوعی
│   ├── موضوعات        (تب‌ها: پیشنهادی / تأییدشده / ردشده)
│   └── تقویم محتوایی
│
├── تولید محتوا
│   ├── صف تولید
│   ├── پیش‌نویس‌ها
│   └── زمان‌بندی‌شده‌ها
│
├── فروشگاه          (فقط در صورت فعال بودن WooCommerce)
│   ├── محصولات
│   └── دسته‌بندی محصولات
│
├── انتشار در شبکه‌ها
│   ├── صف ارسال

│
├── ورود و خروجی

│   └── ورود سرچ کنسول
│
├── گزارش فعالیت
│
└── تنظیمات
    ├── هوش مصنوعی و جستجو   (Providerها، مسیریابی وظایف، پیش‌تنظیم‌ها)
    ├── تصاویر
    ├── یکپارچه‌سازی‌ها
    ├── عملکرد و صف
    ├── مسترپرامپت‌ها        (ContentMaster پیش‌فرض و نسخه‌های سفارشی)
    ├── قالب‌های محتوا       (پیش‌فرض‌های سایت، دسته‌بندی‌ها، قالب‌ها)
    ├── تولید و انتشار
    ├── بودجه و مصرف
```

قوانین:

- وضعیت‌ها (پیشنهادی، تأییدشده، ردشده و…) به‌صورت **تب یا فیلتر** داخل یک صفحه نمایش داده می‌شوند، نه به‌صورت منوی جدا.
- منوها بر اساس ماژول‌های فعال و سطح دسترسی کاربر ساخته می‌شوند.
- کنار هر منو، تعداد موارد نیازمند اقدام (Badge) نمایش داده می‌شود؛ مانند موضوعات منتظر تأیید یا یافته‌های شدت بالا.

## 12.3 پیشخوان و ویجت‌ها

| ویجت | محتوا |
|---|---|
| امتیاز سلامت محتوا | امتیاز 0 تا 100 بر اساس یافته‌های ممیزی وزن‌دار، و روند تغییر آن |
| تکمیل پروفایل | درصد تکمیل و لینک مستقیم به فیلدهای ناقص |
| شروع کار | چک‌لیست مراحل راه‌اندازی تا زمان تکمیل |
| مهم‌ترین یافته‌ها | 5 یافته با شدت بالا و دکمه اقدام |
| محتوای یتیم | تعداد نوشته‌ها و صفحات یتیم |
| منتظر تأیید شما | موضوعات، توضیحات دسته‌بندی، پیشنهادهای لینک و تصاویر |
| صف تولید | در حال اجرا، در انتظار، ناموفق |
| انتشارهای پیش‌رو | 7 روز آینده |
| مصرف و هزینه | مصرف ماه جاری در برابر سقف بودجه، به تفکیک Provider |
| آخرین اسکن | زمان آخرین اسکن و دکمه اسکن مجدد |
| انتشار در شبکه‌ها | ارسال‌های امروز، ارسال‌های ناموفق و کانال‌های قطع |

علاوه بر این، یک ویجت خلاصه (امتیاز سلامت، موارد منتظر تأیید و انتشارهای پیش‌رو) در پیشخوان اصلی وردپرس قرار می‌گیرد که در تنظیمات قابل غیرفعال کردن است.

## 12.4 تجربه اولین اجرا (Onboarding)

1. **صفحه خوش‌آمد** پس از فعال‌سازی: معرفی کوتاه و دکمه «شروع اسکن»
2. **اسکن** در پس‌زمینه با نوار پیشرفت و نمایش زنده تعداد موارد شناسایی‌شده
3. **ویزارد پروفایل** (بخش 4.5)
4. **اولین گزارش سلامت** با 5 اقدام سریع پیشنهادی
5. **چک‌لیست شروع کار** در پیشخوان: تکمیل پروفایل، رفع اولین یافته‌ها، خروجی برای ContentMaster یا اتصال API، تأیید اولین موضوعات

هیچ بخشی از افزونه، به‌جز تنظیمات هوش مصنوعی، برای شروع به کلید API نیاز ندارد.

## 12.5 قوانین ظاهری

**فونت**
- فونت پیش‌فرض: **وزیرمتن (Vazirmatn)** با فایل‌های WOFF2 درون بسته افزونه. بارگذاری از Google Fonts یا CDN خارجی مجاز نیست.
- فونت فقط در صفحات پایدارپرس بارگذاری می‌شود (بر اساس Hook Suffix صفحه). اعمال آن به کل پیشخوان وردپرس با یک گزینه در تنظیمات امکان‌پذیر است.
- ارقام در رابط کاربری فارسی نمایش داده می‌شوند. در کدها، اسلاگ‌ها و آدرس‌ها ارقام لاتین می‌مانند.

**جهت و چیدمان**
- پشتیبانی کامل RTL با CSS Logical Properties
- سایدبار ناوبری در سمت راست
- تاریخ‌ها به شمسی و تاریخ میلادی در Tooltip

**سیستم طراحی**
- استفاده از `@wordpress/components` برای هماهنگی با ظاهر وردپرس، به‌همراه یک لایه Design Token اختصاصی (رنگ، فاصله، شعاع گوشه، سایه)
- رنگ‌های وضعیت ثابت: موفق، هشدار، خطا، اطلاع‌رسانی، در انتظار تأیید
- پشتیبانی از حالت تاریک پیشخوان (در صورت فعال بودن)
- واکنش‌گرا برای عرض تبلت به بالا
- رعایت دسترس‌پذیری: کنتراست کافی، ناوبری با صفحه‌کلید، برچسب‌گذاری فرم‌ها

## 12.6 اصول قابل‌فهم بودن

- تمام رابط کاربری فارسی است و از سیستم ترجمه وردپرس (Text Domain: `paydarpress`) استفاده می‌کند.
- کنار اصطلاحات فنی (Cornerstone، Canonical، Orphan، Cannibalization) یک توضیح کوتاه در Tooltip نمایش داده می‌شود.
- هر یافته ممیزی سه بخش دارد: **مشکل چیست**، **چرا مهم است**، **چه کاری انجام دهم** (با دکمه اقدام).
- صفحات خالی (Empty State) یک توضیح و دکمه قدم بعدی دارند، نه یک جدول خالی.
- عملیات پس‌زمینه وضعیت زنده دارند و پایان آن‌ها با اعلان در پیشخوان اطلاع داده می‌شود.
- پیش از هر عملیات پرهزینه، هزینه تخمینی API نمایش داده و تأیید گرفته می‌شود.
- تغییر در محتوای موجود با Revision وردپرس همراه است و امکان بازگشت دارد.
- عملیات گروهی (Bulk) برای تأیید، رد و اعمال پیشنهادها وجود دارد.
- تعداد گزینه‌های هر صفحه تنظیمات محدود است؛ گزینه‌های کم‌کاربرد در بخش «پیشرفته» قرار می‌گیرند.

## 12.7 سیستم راهنمای درون‌برنامه‌ای (Contextual Help) (جدید)

هدف: کاربر در هیچ صفحه‌ای بدون دانستن «این صفحه چیست و چه کاری باید انجام دهم» رها نشود.

### اجزای راهنما

| جزء | محل | محتوا |
|---|---|---|
| **باکس راهنمای صفحه** | بالای هر صفحه | 2 تا 3 خط: این صفحه چه کاری انجام می‌دهد، چه زمانی از آن استفاده کنم، قدم بعدی چیست |
| **راهنمای فیلد** | زیر هر فیلد تنظیمات | توضیح یک‌خطی، مثال، و مقدار پیشنهادی |
| **Tooltip اصطلاحات** | کنار اصطلاحات فنی | تعریف ساده و یک جمله درباره اهمیت آن |
| **تور معرفی** | اولین ورود به هر بخش اصلی | 3 تا 5 گام که اجزای اصلی صفحه را نشان می‌دهد؛ قابل رد شدن |
| **باکس هشدار** | پیش از عملیات حساس | پیامد عملیات: هزینه API، انتشار خودکار، تغییر مقالات قدیمی، حذف یا ادغام |
| **توضیح غیرفعال بودن** | کنار دکمه‌ها و گزینه‌های غیرفعال | چرا غیرفعال است و چطور فعال می‌شود (مثلاً «برای فعال شدن، ابتدا یک Image Provider تعریف کنید») |
| **صفحه خالی آموزشی** | جدول‌ها و فهرست‌های خالی | توضیح و دکمه قدم بعدی |
| **واژه‌نامه** | صفحه «راهنما» در تنظیمات | تمام اصطلاحات با تعریف ساده |
| **لینک آموزش تکمیلی** | داخل باکس راهنما (اختیاری) | مقاله یا ویدیوی آموزشی در سایت PaydarWP |

نمونه باکس راهنمای صفحه «محتوای یتیم»:

> **محتوای یتیم چیست؟** نوشته‌هایی که هیچ نوشته دیگری به آن‌ها لینک نداده است. گوگل و کاربران این صفحات را سخت‌تر پیدا می‌کنند.
> **چه کار کنم؟** برای هر مورد، روی «پیشنهاد لینک» بزنید و لینک‌های پیشنهادی را تأیید کنید.

### قوانین

- باکس‌ها کوتاه هستند (حداکثر 3 خط). توضیح بیشتر در «بیشتر بدانید» باز می‌شود.
- هر باکس با دکمه «متوجه شدم» بسته می‌شود و با آیکون «؟» در عنوان صفحه دوباره باز می‌شود.
- وضعیت بسته بودن هر راهنما **برای هر کاربر جداگانه** در User Meta (`paydarpress_dismissed_help`) ذخیره می‌شود؛ همکار جدید همه راهنماها را می‌بیند.
- گزینه «نمایش دوباره همه راهنماها» در تنظیمات کاربر وجود دارد.
- **حالت ساده / حرفه‌ای:** در حالت ساده (پیش‌فرض برای کاربران جدید)، گزینه‌های پیشرفته پنهان و راهنماها فعال هستند. در حالت حرفه‌ای، راهنماها جمع‌شده و همه گزینه‌ها نمایش داده می‌شوند.
- متن راهنماها در کد ثابت نوشته نمی‌شود. محتوای راهنما در فایل‌های JSON در پوشه `help/` نگهداری می‌شود، با کلید هر صفحه و فیلد، از طریق سیستم ترجمه وردپرس قابل ترجمه است و با هر بروزرسانی افزونه بروز می‌شود.
- راهنماها لحن ساده، فارسی روان و بدون اصطلاح انگلیسی توضیح‌داده‌نشده دارند.

# 13. امنیت و کنترل دسترسی (Security)

امنیت برای یک افزونه تجاری که امکان انتشار و تغییر محتوای سایت را دارد، الزامی است.

### الزامات

1. استفاده از WordPress Nonces برای درخواست‌های مدیریتی.
2. بررسی Capability کاربران قبل از هر عملیات.
3. اعتبارسنجی ورودی‌ها.
4. Sanitization داده‌ها.
5. Escape خروجی‌ها.
6. استفاده از Prepared Statements.
7. نگهداری API Key و توکن کانال‌ها در سمت سرور به‌صورت رمزگذاری‌شده، و عدم نمایش کامل آن‌ها در رابط کاربری پس از ذخیره.
8. جلوگیری از دسترسی مستقیم به فایل‌های داخلی.
9. محدود کردن دسترسی به REST API.
10. ثبت عملیات حساس در Activity Log.

### سطح دسترسی پیشنهادی

- Administrator: مدیریت کامل
- Content Manager: مدیریت تولید و انتشار محتوا
- SEO Manager: مدیریت تحقیق و تحلیل سئو
- Viewer: مشاهده گزارش‌ها

مجوزهای اختصاصی باید از طریق Capabilities قابل تنظیم باشند.

هیچ درخواست AI نباید مستقیماً به اجرای SQL یا دسترسی نامحدود به فایل‌های سایت منجر شود.

تمام عملیات نوشتن باید از طریق Actionهای محدود و تعریف‌شده انجام شوند.

### فایل‌های ورودی

فایل‌های ورودی (JSON از ContentMaster و CSV از Search Console) داده غیرقابل اعتماد محسوب می‌شوند:

- اعتبارسنجی کامل با Schema پیش از پردازش
- پاک‌سازی HTML با `wp_kses_post`
- ایجاد محتوا فقط به‌صورت پیش‌نویس، صرف‌نظر از وضعیت درج‌شده در فایل
- عدم پذیرش Meta Keyهای دلخواه و فقط نوشتن در فیلدهای تعریف‌شده
- عدم پذیرش لینک‌های داخلی به آدرس‌های ناموجود
- محدودیت حجم فایل و تعداد رکورد
- ثبت هر ورود در Activity Log

# 19. الزامات کیفیت و پایداری (Non-Functional Requirements)

پایدارپرس باید شرایط زیر را رعایت کند:

**Performance**
- عدم اسکن کامل سایت در هر درخواست.
- استفاده از پردازش افزایشی.
- صفحه‌بندی داده‌های حجیم.
- جلوگیری از درخواست‌های غیرضروری به AI.
- اجرای عملیات سنگین در Background.

### Performance Budget (جدید)

پایدارپرس ابزار مدیریتی است و نباید هیچ اثر محسوسی بر سرعت سایت برای بازدیدکنندگان داشته باشد.

**بخش عمومی سایت (Frontend)**
- هیچ فایل CSS، JavaScript یا فونتی در بخش عمومی سایت بارگذاری نمی‌شود.
- هیچ کوئری پایدارپرس در بارگذاری صفحات عمومی اجرا نمی‌شود.
- هیچ درخواست HTTP خارجی در زمان بارگذاری صفحات عمومی ارسال نمی‌شود.

**پیشخوان وردپرس**
- فایل‌ها فقط در صفحات پایدارپرس بارگذاری می‌شوند. ویجت پیشخوان وردپرس فقط داده ذخیره‌شده را نمایش می‌دهد و محاسبه سنگین انجام نمی‌دهد.
- Optionهای حجیم با `autoload = no` ذخیره می‌شوند.
- داده‌های جدول‌ها با صفحه‌بندی سمت سرور و از طریق REST API بارگذاری می‌شوند.
- آمار پیشخوان پس از هر اسکن محاسبه و ذخیره می‌شود و در هر بار باز شدن صفحه دوباره محاسبه نمی‌شود.

**Hookهای ذخیره و انتشار**
- Hookهایی مانند `save_post` و `transition_post_status` فقط یک Job در صف ثبت می‌کنند و هیچ پردازش سنگین یا درخواست خارجی انجام نمی‌دهند. ذخیره نوشته توسط کاربر هرگز کند نمی‌شود.

**صف پس‌زمینه**
- اندازه Batch، تعداد Job هم‌زمان و حداکثر زمان اجرای هر Batch قابل تنظیم است.
- **حالت هاست اشتراکی:** Batch کوچک، یک Job هم‌زمان و مکث کوتاه بین Batchها
- امکان محدود کردن اسکن کامل و پردازش‌های سنگین به ساعات کم‌ترافیک
- کنترل مصرف حافظه در پردازش تصاویر (پردازش تک‌به‌تک، آزادسازی منابع)
- اتصال به Cron واقعی سرور برای جدا شدن صف از ترافیک سایت

**دیتابیس**
- Index برای فیلدهای پرتکرار (شناسه محتوا، وضعیت، تاریخ، نوع)
- **سیاست نگهداری داده:** حذف خودکار گزارش‌های فعالیت، سوابق مصرف، لاگ توزیع و Jobهای کامل‌شده قدیمی‌تر از بازه قابل تنظیم (پیش‌فرض 90 روز)
- استفاده از Object Cache وردپرس در صورت وجود

**پایش سلامت افزونه**

صفحه «پیشرفته» وضعیت فنی را نمایش می‌دهد: طول صف، Jobهای ناموفق، حجم جداول پایدارپرس، زمان آخرین اجرای Cron و هشدار در صورت توقف صف.

**اثر مثبت بر سرعت سایت**

تصاویر تولیدشده با فرمت WebP، ابعاد دقیق، width و height و اندازه‌های واکنش‌گرا (srcset وردپرس) ذخیره می‌شوند و ممیزی تصاویر، فایل‌های حجیم موجود را برای بهینه‌سازی معرفی می‌کند.

**معیار پذیرش عملکرد**

فعال بودن پایدارپرس نباید تعداد کوئری‌ها یا زمان پاسخ صفحات عمومی سایت را به‌صورت قابل اندازه‌گیری افزایش دهد. این مورد پیش از هر انتشار با ابزاری مانند Query Monitor آزموده می‌شود.


**Reliability**
- امکان ادامه پردازش پس از خطا.
- جلوگیری از اجرای تکراری Job.
- ثبت وضعیت هر عملیات.
- مدیریت درخواست‌های Timeout.
- حفظ اطلاعات در صورت قطع API.

**Scalability**
- پشتیبانی از سایت‌های کوچک و بزرگ.
- امکان پردازش چند مقاله در صف.
- قابلیت توسعه ماژول‌های مستقل.
- مدیریت مصرف منابع سرور.

**Maintainability**
- جداسازی منطق هر ماژول.
- استفاده از Interfaceهای مشخص.
- تست واحد و یکپارچه.
- مستندسازی APIهای داخلی.
- مدیریت نسخه دیتابیس.

**Data Integrity**
- جلوگیری از انتشار محتوای ناقص.
- حفظ شناسه و ارتباط محتواها.
- ثبت تغییرات مهم.
- امکان بازیابی وضعیت قبلی در عملیات حساس.

# 21. معیارهای پذیرش نسخه اولیه (Version 1.0 Acceptance Criteria)

نسخه اولیه زمانی قابل قبول است که:

1. افزونه بدون وابستگی به PaydarWP روی وردپرس نصب شود.
2. اطلاعات عمومی سایت را شناسایی کند.
3. تمام مقالات را با وضعیت انتشار استخراج کند.
4. دسته‌بندی‌ها و برچسب‌ها را استخراج کند.
5. در صورت وجود WooCommerce محصولات را شناسایی کند.
6. دسته‌بندی محصولات را استخراج کند.
7. اطلاعات سئو را در صورت وجود افزونه‌های پشتیبانی‌شده بخواند.
8. اطلاعات را در ساختار داخلی پایدارپرس نگهداری کند.
9. امکان بروزرسانی اطلاعات موجودی وجود داشته باشد.
10. خروجی JSON معتبر و کامل تولید شود.
11. امکان انتخاب بخش‌های موردنیاز برای Export وجود داشته باشد.
12. اطلاعات حساس و کلیدهای API وارد خروجی نشوند.
13. اسکن سایت‌های بزرگ بدون محدودیت زمانی یک درخواست PHP انجام شود.
14. پس از غیرفعال‌سازی افزونه، اطلاعات اصلی وردپرس دست‌نخورده باقی بمانند.
15. صفحات کلیدی و CTAها را از منو و اسلاگ‌ها پیشنهاد دهد و فیلدهای پروفایل را با source و confirmed ذخیره کند.
16. ویزارد راه‌اندازی، پروفایل را در کمتر از 5 مرحله کامل کند و فیلدهای ناقص را در `missing_fields` ثبت کند.
17. Health Audit تمام بررسی‌های بخش 4.6 را بدون هیچ درخواست خارجی اجرا کند.
18. محتوای ساخته‌شده با Elementor به‌درستی اسکن شود (سرفصل‌ها، لینک‌ها، تعداد کلمات).
19. تشخیص تکرار و تطبیق برچسب‌ها پس از نرمال‌سازی فارسی انجام شود.
20. خروجی `contentmaster-lite` مستقیماً توسط ContentMaster قابل خواندن باشد.
21. افزونه زیر منوی «پایدار وردپرس» قرار بگیرد و نصب هم‌زمان با محصول دیگر PaydarWP بدون تداخل جدول، Option، Hook یا منو انجام شود.
22. رابط کاربری کاملاً فارسی و RTL باشد و وزیرمتن از فایل‌های داخلی افزونه و فقط در صفحات پایدارپرس بارگذاری شود.
23. نوشته‌ها، برگه‌ها و محصولات یتیم با فهرست مقالات پیشنهادی برای لینک‌دهی نمایش داده شوند.
24. دسته‌بندی‌ها و برچسب‌های خالی، ضعیف و تکراری با اقدام پیشنهادی شناسایی شوند.
25. تصاویر بدون Alt یا با Alt بی‌معنا، هم در تصویر شاخص و هم داخل متن، شناسایی شوند.
26. فعال بودن افزونه هیچ فایل یا کوئری اضافه‌ای در بخش عمومی سایت ایجاد نکند.
27. ذخیره نوشته توسط کاربر با فعال بودن افزونه به‌صورت محسوس کند نشود.
28. اسکن کامل سایت در حالت هاست اشتراکی بدون خطای زمان اجرا یا حافظه کامل شود.
29. هر صفحه اصلی افزونه باکس راهنما داشته باشد و هر فیلد تنظیمات توضیح داشته باشد.
30. وضعیت بسته شدن راهنماها برای هر کاربر جداگانه ذخیره شود.
31. ContentMaster به‌عنوان الگوی پیش‌فرض نصب شود و تغییرات مدیر نسخه پیش‌فرض را بازنویسی نکند.
32. در هر تولید فقط متغیرهای مجاز و در بازه تعیین‌شده قابل تغییر باشند و قوانین قفل‌شده در هیچ حالتی تغییر نکنند.
33. وضعیت دسترسی خزنده‌های گوگل و هوش مصنوعی در robots.txt نمایش داده شود.
34. مقالات منتشرشده امتیاز نیاز به بروزرسانی و اقدام پیشنهادی داشته باشند.
35. نویسنده و بازبین فقط از کاربران واقعی سایت قابل انتخاب باشند.
